项目复盘｜中南民大微服务：异常返校检测与企微闭环预警系统

7 月初接到了一个紧急任务：学校需要上线一套**“异常返校信息监测系统”**（微服务代号：20260705）。

业务场景其实很现实：部分因休学、校外就医或特殊情况报备在案的学生，在未经许可的情况下私自返回了校园。以前这类情况基本靠人工排查或者事后宿管对账，滞后性严重。学校希望一旦这类在册学生在校门口刷了门禁闸机（比如南湖校区南大门进站闸机），或者在食堂、超市刷了校园卡消费，系统必须在秒级捕获异常，并第一时间把预警卡片精准推送到对应学院辅导员的企业微信上，辅导员在手机上点一下就能完成核实留痕。

整个项目从数据库表设计、微服务后端、企微消息管道打通，到前端管理后台落地，全部跑在学校现有的微服务体系（wfw.scuec.edu.cn）里。

现在系统平稳上线跑了一段时间，趁着记忆犹新，写篇接地气的技术复盘。不谈假大空的高大上理论，只聊真实的系统链路，以及开发过程中那几把让人掉头发的“暗坑”。

一、 核心业务链路与架构设计

整个系统的闭环链路非常直接，可以概括为三步走：名单布控 -> 底层捕获 -> 企微推送与移动端一键留痕。

1. 核心数据模型设计

业务主要依托 Oracle 下的 USR_WFW 用户空间，核心三张表：

  • T_YCFX_RY（异常返校布控名单表）：
    存储重点关注学生的学号（SFRZH）、姓名（XM）、学院代码（DWDM）、班级、管控状态（用操作类型 CZLX 标记，I/U 为在控，D 为移出管控）以及备注留痕。
  • T_YCFX_HDJL（异常返校活动/预警记录表）：
    捕获到的异常事件。核心字段包括：活动类型（HDLX：0-门禁，1-消费）、活动时间（HDSJ）、活动地点（HDDD）、推送状态（TSZT：0-待推送，1-已推送，2-异常无接收人忽略）、处理状态（CLZT：0-未处理，1-已处理）、操作人及时间。
  • T_YCFX_GLY（学院二级管理员配置表）：
    用来绑定每个学院（DWDM）由哪几位辅导员（SFRZH）接收预警，支撑消息路由。

二、 实战排雷录：这几个暗坑让人印象深刻

写基础增删改查并不难，难的是各种边缘情况、奇葩协议对接以及多系统整合时的“水土不服”。

1. 企微卡片直达 vs CAS SSO 的“死锁”

这是整个系统开发时最大的交互痛点。

原始设想：辅导员收到企微通知后，点击卡片链接跳转到管理后台登录 CAS，查看记录并点击“确认已联系学生”。
现场打脸：辅导员通常是在走廊、食堂或下班路上看手机，企微内置浏览器打开 CAS 认证经常出现 Cookie 丢失、多重重定向甚至验证码打不开的情况。辅导员反馈：“我人在外面就想快速点一下确认收到，你让我重新输两遍统一身份认证密码？”

解法：手搓 HMAC-SHA256 静默签名链接
为了彻底甩掉移动端登录包袱，同时防止链接被遍历或伪造攻击，我们在推送卡片时采用了轻量级免登验签机制：

每个推送卡片的跳转 URL 直接拼装为：
https://wfw.scuec.edu.cn/v2/2026/07/05_notify/wechat_confirm?record_id=xxx&sfrzh=xxx&sign=hash

辅导员点开后，后端的 wechat_confirm 接口执行三道防线：

  1. 校验 URL 中的 sign 是否与服务端现场计算一致（防篡改与遍历）；
  2. 查库校验当前 sfrzh 是否属于该学生所在学院的在册管理员（防越权）；
  3. 校验通过后，直接在后台将预警记录更新为 CLZT = '1'，记录处理人工号与时间，当场返回一个极简的绿色确认成功页面。

辅导员不用输入任何账号密码，从收到通知到完成核实留痕，只需要 1 秒钟。

2. 权限继承的“降级陷阱”与虚拟权限 999

学校微服务底层有一个通用的权限管理体系（代号 0104），按 0（超管）、1（一级管理员）、2（二级管理员）来划分。

但在我们这个特定业务里出现了一个很尴尬的冲突：

  • 异常返校系统需要各学院辅导员自己登录上来维护本学院的管控学生名单；
  • 如果给所有辅导员都在全局系统里开通“二级管理员（2）”，会污染其他微服务的权限体系；
  • 更坑的是，某些原本拥有全局超管权限的老师，因为兼任了某个学院的负责人，在查完学院绑定后，权限字段居然会被底层逻辑覆盖降级成普通二级管理员！

解法：自建私有化隔离 + 权限防御
我们在 05.pm 的 auto 鉴权入口层做了两层兜底：

  2. 虚拟权限标号 999：
    如果当前老师在全局系统中没有微服务管理员权限，但在本系统的私有表 T_YCFX_GLY 中存在记录，我们动态赋予其内部虚拟权限码 999，并提取其分管的学院代码（DWDM）。后续所有的 SQL 查询（预警查询、名单添加、软删除）强制拼接：

既做到了辅导员只能看和管自己学院的学生，又完全不破坏全局微服务的权限大盘。

3. Excel 导出中的长工号“科学计数法”惨案

学生管理系统少不了数据导出功能。一开始测试导出 Excel 时，辅导员反馈：“导出来的学号怎么全变成了 2.02521E+11？后四位全丢了！”

学号和工号通常长达 12 位（比如 202521111028），直接生成 CSV 或者普通 HTML 表格时，微软 Excel 会自作聪明地将其识别为大数字并转为科学计数法。

如果通过 Perl 装 Spreadsheet::WriteExcel 这种重型模块，又会受制于线上容器只读依赖的问题。

解法：标准 HTML-Excel + mso 样式注入
直接输出带 Office 命名空间的 HTML 表格，并利用微软私有的 CSS 规则 mso-number-format，强制声明单元格格式为纯文本：

在渲染学号、工号和日期的 <td> 上打上 class="text"，辅导员无论用 WPS 还是微软 Excel 打开，12 位学号都整整齐齐，再也不会被截断破坏。

4. 预警死循环防重设计

底层数据扫描脚本跑定时任务时，如果某个休学学生触发了门禁，但该学生所属学院在系统上线初期还没有配置任何辅导员接收人，会发生什么？

如果代码写成：
if (@recipients > 0) { 发送并更新 TSZT='1' }
那么当 @recipients == 0 时，该记录的状态就会一直停留在 TSZT='0'。下一次定时扫描进来，它又被捞出来……如此循环往复，后台日志不仅被疯狂刷爆，数据库也会不断执行空轮询。

三、 前端架构：轻量级 Vue 3 极简嵌入

后台页面跑在服务端模板渲染的容器内，如果搞一套需要打包编译的工程化代码，生产部署时根本没有 npm 环境来跑构建。

为了兼顾开发速度与交互体验，我们采取了一个折中但高效的方案：

  • 在服务端模板（05.tt2）中，直接通过静态资源引入单文件版 Vue 3：<script src=".../vue.global.js"></script>。
  • 利用 Vue 3 的 Composition API (setup, ref, computed, watch) 接管页面的全部交互。
  • 所有的预警列表筛选、未处理条数 Badge 徽标计算、添加管控学生弹窗、二级管理员维护，全部做成 SPA 级别的异步交互（Fetch API）。

这样做的巨大收益：

  1. 零构建产物：没有 dist 目录，没有繁重的打包配置，模板文件一存即生效；
  2. 丝滑体验：辅导员在处理预警、切换 Tab、搜索过滤时全是局部渲染，没有白屏闪烁；
  3. 维护成本极低：前后端所有变动都收敛在单个控制器（05.pm）和单个模板（05.tt2）内，不管是查 bug 还是迁移部署，心智负担降到了最低。

四、 写在最后

复盘这个项目，没有炫技的新框架，也没有过度设计的分层架构。整个系统围绕 Oracle 存储、后端业务网关、微信 UMS 推送通道以及轻盈的 Vue 3 前端展开，没有花哨的概念，全是扎扎实实的业务闭环。

但对用户（学生工作部、各学院辅导员）来说：

  • 学生一旦发生异常刷卡，10 秒内辅导员企微必定震动；
  • 辅导员在手机上点一下，不需要二次登录，立刻完成研判和留痕；
  • 院系管理员在电脑上打开后台，数据条理清晰，导出表格开箱即用。

真正的工程价值往往不在于你在简历上吹了多少新名词，而在于在现有的客观业务约束下，能不能拿出最克制、最健壮的方案，把现实问题干脆利落地解决掉。
